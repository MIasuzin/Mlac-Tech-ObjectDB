# Формат файла MTDB

Документ описывает формат `.mtdb` версии **3**. Многобайтовые числа записываются в little-endian. Формат версии 2 читается только внутренним механизмом отдельной офлайн-миграции; публичный `mtdb.open()` не открывает v2 для обычной работы.

## Размещение данных

| Область | Смещение | Размер |
| --- | ---: | ---: |
| Заголовок | `0` | `4096` байт |
| Индекс: 65 536 корзин по 8 байт | `4096` | `524288` байт |
| Журнал записей | `528384` | до конца файла |

Файл короче `528384` байт некорректен. Пустой журнал допустим. Обычные записи дописываются в конец; старые версии не перезаписываются при изменении документа.

## Заголовок

| Смещение | Длина | Значение |
| ---: | ---: | --- |
| `0` | 4 | ASCII `MTDB` |
| `4` | 4 | Номер формата: `3` (`uint32`) |
| `8` | 4 | Число корзин: `65536` (`uint32`) |
| `12` | 1 | Состояние: `0` = `CLEAN`, `1` = `DIRTY` |
| `13` | 3 | Резерв |
| `16` | 8 | Начало журнала: `528384` (`uint64`) |
| `24` | 8 | Резерв |
| `32` | 32 | Слот метаданных A |
| `64` | 32 | Слот метаданных B |
| `96` | `4000` | Резерв |

Новый файл содержит два слота с поколениями `1` и `0`. При чтении выбирается корректный слот с наибольшим поколением; запись обновляет другой слот и синхронизирует файл. В отдельном байте `12` также хранится состояние. При несовпадении состояния, размера файла или контрольной суммы индекса с метаданными MTDB восстанавливает индекс по подтверждённому журналу.

### Слот метаданных (32 байта)

| Смещение внутри слота | Длина | Значение |
| ---: | ---: | --- |
| `0` | 8 | Номер поколения (`uint64`) |
| `8` | 1 | `CLEAN` / `DIRTY` |
| `9` | 7 | Нули |
| `16` | 8 | Размер файла на момент записи слота (`uint64`) |
| `24` | 4 | CRC32 512 KiB индекса в состоянии `CLEAN`; при записи `DIRTY` — `0` |
| `28` | 4 | CRC32 байтов `0..27` этого слота |

Валидный слот имеет допустимое состояние, нулевые зарезервированные байты, корректную CRC32 и размер файла не меньше `528384`, помещающийся в безопасное целое число JavaScript. Два повреждённых слота сами по себе не означают, что можно отбросить подтверждённые данные: восстановление сначала проверяет журнал.

## Индекс и пути

Каждая корзина индекса — `uint64` со смещением новейшей **обычной** записи в журнале; `0` означает пустую корзину. Адрес корзины: `4096 + 8 × bucket`. Выбор корзины:

```text
bucket = FNV1a32(UTF8(normalizedPath)) % 65536
```

Функция использует начальное значение `0x811C9DC5`, XOR очередного байта и умножение по модулю `2^32` на `0x01000193`. Коллизии разрешает `previousOffset`: каждая обычная запись указывает на предыдущую голову **своей** корзины. Смещение должно быть строго меньше смещения текущей записи; `0` завершает цепочку.

Индекс на диске — восстанавливаемое производное журнала, а не отдельный источник истины. Открытая база держит его 512 KiB в памяти и синхронизирует после изменения файла. Дополнительно при открытии по журналу строится непостоянный индекс живых путей в памяти. Он не меняет формат `.mtdb` и пересоздаётся после открытия, восстановления и замены файла при компактизации.

Путь кодируется UTF-8; предел — 1024 байта. Путь обычной записи нормализован, документ `WRITE` оканчивается на `.json` (без учёта регистра). Путь меток транзакции всегда `@tx`. Корень каталога существует неявно и отдельной записью не хранится.

## Запись журнала

Каждая запись состоит из заголовка длиной 32 байта, `pathLength` байтов пути и `dataLength` байтов данных. Общая длина — `32 + pathLength + dataLength`.

| Смещение в записи | Длина | Значение |
| ---: | ---: | --- |
| `0` | 4 | ASCII `MTR1` |
| `4` | 1 | Тип записи |
| `5` | 3 | Нули |
| `8` | 4 | Длина пути (`uint32`) |
| `12` | 4 | Длина данных (`uint32`) |
| `16` | 8 | `previousOffset` (`uint64`) |
| `24` | 4 | CRC32 записи (`uint32`) |
| `28` | 4 | Нули |

CRC32 считается по 17 байтам метаданных `type (1) + pathLength (4) + dataLength (4) + previousOffset (8)`, затем по байтам пути и данным. В CRC32 записи не входят `MTR1`, резервные байты и само поле CRC32. Для каждого `WRITE` данные — сериализованный JSON не более 100 MiB.

| Тип | Число | Путь | Данные | Смысл |
| --- | ---: | --- | --- | --- |
| `DIRECTORY` | `1` | путь каталога | нет | Создать каталог |
| `WRITE` | `2` | путь `.json` | UTF-8 JSON | Создать или заменить документ |
| `DELETE` | `3` | путь документа либо каталога | нет | Удалить путь |
| `COMMIT` | `4` | путь предшествующей записи | нет | Подтвердить одиночное изменение |
| `TX_BEGIN` | `5` | `@tx` | 8 байт | Начало атомарной группы |
| `TX_COMMIT` | `6` | `@tx` | 4 байта | Подтвердить атомарную группу |

`COMMIT.previousOffset` указывает на непосредственно предшествующую обычную запись. Обычная запись в этом случае содержит прежнюю голову корзины; ни `COMMIT`, ни метки `TX_*` не становятся головой корзины.

### Одиночное изменение

```text
пометить базу DIRTY и синхронизировать метаданные
записать DIRECTORY / WRITE / DELETE
записать COMMIT с тем же путём и адресом изменения
fsync файла с журналом
обновить голову корзины в индексе
fsync файла с индексом
```

Восстановление применяет только изменение с корректным `COMMIT`. Неоконченное изменение в конце журнала может быть отсечено. Подтверждённое повреждение или ошибка структуры не скрываются усечением.

### Атомарная группа (v3)

```text
TX_BEGIN → mutation[0] → … → mutation[count-1] → TX_COMMIT
```

- Данные `TX_BEGIN`: `count` (`uint32`, байты `0..3`) и `mutationBytes` (`uint32`, байты `4..7`). `previousOffset = 0`.
- Следуют ровно `count` записей типов `WRITE`, `DELETE` или `DIRECTORY` без отдельных `COMMIT`. `previousOffset` каждой указывает на последнюю запись её корзины, включая предшествующие изменения в этой группе.
- Данные `TX_COMMIT`: CRC32 **полных сериализованных байтов** `TX_BEGIN` и всех записей группы (`uint32`). `previousOffset` указывает на начало `TX_BEGIN`.
- После записи всей группы выполняется `fsync` журнала, обновляются затронутые корзины и выполняется второй `fsync`. Только затем вызов завершается успешно.
- При восстановлении проверяются размер группы, число и уникальность изменённых путей, последовательность корзин, CRC32 группы и допустимость каждого изменения. Либо применяется вся группа, либо она не применяется.

Публичный `db.transaction()` принимает не более 1000 изменяемых путей и 128 MiB подготовленных данных. Рекурсивный `rmdir()` использует тот же формат с отдельным внутренним пределом **100 001 запись** (100 000 дочерних путей и сам каталог), сохраняя общий предел 128 MiB. Поэтому проверка журнала допускает внутренний предел, хотя пользовательская транзакция ограничена 1000 путями.

## Восстановление и проверка

При обнаружении `DIRTY`, несовпадения размера, CRC32 индекса или повреждённых слотов MTDB последовательно проверяет журнал, сохраняет подтверждённые изменения, отсекает распознаваемый незавершённый хвост и пересобирает индекс. Изменённый индекс синхронизируется с файлом; затем записывается согласованное `CLEAN` состояние.

При проверке дополнительно сравниваются физический размер и CRC32 индекса с активным слотом, корректность всех записей и JSON, последовательность подтверждений, родительские каталоги и итоговые головы корзин. Подтверждённое повреждение журнала приводит к ошибке, а не к молчаливому пропуску записи.

Файл с записью об ошибке после неудачного изменения требуется закрыть и снова открыть перед дальнейшей работой. Если запись вернула успех, библиотека уже выполнила оба предусмотренных `fsync`; поведение при отказе питания дополнительно зависит от гарантий ОС и носителя.

## Компактизация и вспомогательные файлы

Компактизация происходит автоматически в рабочем потоке: сохраняются текущие документы и каталоги, удаляются исторические версии и метки удаления, пересоздаются цепочки и пары `запись + COMMIT`. Новый файл проверяется до замены основного; текущие записи, добавленные во время обработки снимка, догоняются до замены. Ошибка временного чтения в потоке обслуживания отражается в `db.stats().maintenanceError` и сама по себе не останавливает работу основного экземпляра.

Для создания и обслуживания используются временные файлы около `.mtdb`: `.create.tmp`, `.compact.tmp`, `.compact-<uuid>.mtdb`, `.lock`, `.lock.guard`, а при атомарной публикации блокировки — кратковременные `.lock.<token>.tmp` и `.lock.guard.<token>.tmp`. Они не являются частью формата базы. При сбое временный файл блокировки может остаться; содержимое `.mtdb` определяется только заголовком, индексом и журналом.

Блокировка содержит PID, случайный токен и идентификатор запуска процесса. Старые корректные блокировки без идентификатора читаются для совместимости. Если нельзя надёжно определить владельца блокировки, открытие завершается отказом, чтобы не допустить одновременно двух писателей.

## Совместимость

Формат v3 расширяет журнал записями `TX_BEGIN` и `TX_COMMIT`. Читатель формата v2 не должен открывать файл v3. База v2 должна быть переведена в v3 отдельной офлайн-миграцией на резервной копии; проверка номера версии сама по себе миграцию не выполняет. Версия формата файла не совпадает с номером версии npm-пакета.
