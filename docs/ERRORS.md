# Ошибки MTDB

Методы MTDB выбрасывают обычный `Error` со строковым свойством `error.code`. Проверяйте **точное значение** кода: большинство кодов в текущей реализации записано в нижнем регистре; префикс `MTDB_` имеют только несколько кодов. В старых версиях этого документа они приводились в другом виде.

```js
try {
  db.write('users/42.json', {id: 42});
}

catch (error) {
  if (error.code === 'directory_not_found') {
    db.mkdir('users');
  }

  else {
    throw error;
  }
}
```

`error.message` предназначено для человека и не является стабильным интерфейсом. `error.cause` может содержать исходную ошибку, а `error.offset` — смещение проблемного участка при проверке файла; эти дополнительные поля есть не у каждой ошибки. Низкоуровневые ошибки ОС (`EIO`, `ENOSPC`, `EACCES` и другие) также могут передаваться без замены их `code`.

## Пути, документы и каталоги

| `error.code` | Причина |
| --- | --- |
| `invalid_file_path` | Аргумент `open()` не является непустым путём |
| `invalid_file_extension` | Файл базы не оканчивается на `.mtdb` |
| `invalid_path` | Некорректный внутренний путь, запрещённый сегмент или управляющий символ |
| `path_too_long` | Исходный внутренний путь превышает 1024 байта UTF-8 |
| `json_extension_required` | Путь документа не оканчивается на `.json` |
| `invalid_json` | Значение нельзя сериализовать через `JSON.stringify()` |
| `json_too_large` | Сериализованный JSON превышает 100 MiB |
| `directory_not_found` | Требуемый каталог или родитель документа отсутствует |
| `directory_not_empty` | Вызван `rmdir()` для непустого каталога без `{recursive: true}` |
| `path_is_file` | Там, где требуется каталог, находится документ |
| `path_is_directory` | Там, где требуется документ, находится каталог |
| `invalid_list_options` | Недопустимые параметры `list()` |
| `invalid_rmdir_options` | Недопустимые параметры `rmdir()` |

У `has()` допустим путь каталога и пустая строка для корня. Ограничение `.json` применяется к `read()`, `write()`, `delete()` и документным методам транзакции.

## Транзакции и состояние экземпляра

| `error.code` | Причина |
| --- | --- |
| `MTDB_INVALID_TRANSACTION` | Обработчик транзакции не является функцией |
| `MTDB_ASYNC_TRANSACTION_NOT_SUPPORTED` | Обработчик вернул `Promise` или другую асинхронную работу |
| `MTDB_NESTED_TRANSACTION` | Вызвана вложенная транзакция |
| `MTDB_TRANSACTION_CLOSED` | Метод объекта `tx` вызван после завершения обработчика |
| `MTDB_TRANSACTION_TOO_LARGE` | Превышен лимит числа путей или суммарного размера транзакции/рекурсивного удаления |
| `reentrant_operation` | Метод базы вызван внутри другой операции с тем же экземпляром |
| `closed` | Используется закрытая база |
| `recovery_required` | После опасной ошибки запись/чтение остановлены до закрытия и открытия файла |
| `operation_outcome_unknown` | Индекс удалось восстановить, но исход изменяющей операции не подтверждён |

Публичная `transaction()` ограничена 1000 путями и 128 MiB подготовленных данных. Рекурсивный `rmdir()` имеет внутренний предел 100 000 дочерних записей плюс запись удаляемого каталога и тот же предел 128 MiB. При `MTDB_TRANSACTION_TOO_LARGE` рекурсивное удаление не применяется частично.

## Блокировка и файл базы

| `error.code` | Причина |
| --- | --- |
| `MTDB_DATABASE_LOCKED` | Другой процесс уже держит блокировку, создание lock ещё идёт либо нельзя безопасно установить владельца |
| `corrupted_lock` | Данные файла блокировки недействительны |
| `lock_changed` | Файл блокировки исчез или изменился во время внутренней проверки |
| `lock_ownership_lost` | При освобождении блокировка принадлежит другому владельцу |
| `file_changed` | Файл базы изменился между разрешением пути и открытием |
| `symlink_unsupported` | База открыта через неподдерживаемую символьную ссылку |
| `hardlink_unsupported` | У файла базы есть несколько жёстких ссылок |
| `path_not_file` | Путь базы не указывает на обычный файл |
| `unsupported_version` | Формат файла не поддерживается публичным открытием; v2 требует отдельной миграции |

После отказа при проверке чужого lock не удаляйте его, пока не убедились, что другой процесс уже не работает с этой базой. Для старого lock без записанного идентификатора процесса повторно использованный PID неотличим от прежнего владельца автоматически.

## Повреждения и ввод-вывод

| `error.code` | Причина |
| --- | --- |
| `corrupted_file` | Файл меньше минимального размера или снимок имеет неверную длину |
| `invalid_magic` | Неверная сигнатура `.mtdb` |
| `invalid_header` | Некорректный заголовок, метаданные или размер подтверждённого файла |
| `invalid_header_state` | Некорректное состояние `CLEAN`/`DIRTY` |
| `invalid_index` | Недопустимые параметры индекса |
| `corrupted_index` | Индекс не согласован с журналом или цепочка корзины недействительна |
| `corrupted_record` | Повреждена запись, путь, заголовок или CRC32 записи |
| `corrupted_json` | Сохранённые данные нельзя разобрать как корректный JSON |
| `corrupted_log` | Нарушена структура подтверждений, последовательность или CRC32 транзакции |
| `unexpected_eof` | Низкоуровневое чтение завершилось раньше ожидаемого |
| `write_failed` | Низкоуровневая запись не завершена |

Подтверждённые повреждённые данные не пропускаются молча. `verify()` и `stats()` выполняют полный проход и могут выбросить любую из соответствующих ошибок.

## Внутренние ошибки и обслуживание

Эти коды существуют в исходниках, но обычно не являются результатом корректного вызова публичного API:

| `error.code` | Причина |
| --- | --- |
| `invalid_record_type` | Внутренний код получил недопустимый тип создаваемой записи |
| `invalid_record_path` | Внутренний код получил недопустимый путь создаваемой записи |
| `invalid_record_data` | Внутренний код получил недопустимые данные создаваемой записи |
| `invalid_record_offset` | Внутренний код получил недопустимое смещение |
| `compact_failed` | Не удалось обработать или заменить файл компактизации |
| `compact_validation_failed` | Подготовленный файл компактизации не прошёл проверку |

Компактизация работает в фоновом потоке. Её ошибка обычно записывается в `db.stats().maintenanceError` как `{code, message}`, а не выбрасывается вызовом `write()`. Там может появиться исходный код ОС, `corrupted_snapshot`, `maintenance_failed`, `worker_start_failed`, `worker_error`, `worker_exit`, `worker_message_failed` или `compact_failed`. Разовый сбой чтения вроде `EIO` в фоновом потоке сам по себе не переводит основной экземпляр в `recovery_required`; подтверждённое повреждение источника может перевести.

## Что делать после ошибки

| Ситуация | Действие |
| --- | --- |
| Неправильный путь, JSON, опции или нарушение лимита до записи | Исправить аргументы; базой можно пользоваться дальше |
| `directory_not_found`, `directory_not_empty`, `path_is_file`, `path_is_directory` | Исправить последовательность действий или структуру путей |
| `MTDB_DATABASE_LOCKED` | Освободить базу в другом процессе или дождаться окончания создания блокировки |
| `operation_outcome_unknown` | Закрыть базу, открыть снова и проверить фактическое состояние пути; не повторять платёж/операцию вслепую |
| `recovery_required`, неизвестная ошибка записи или `fsync` | Прекратить операции, попытаться закрыть экземпляр, открыть файл заново и проверить данные |
| Ошибка проверки целостности подтверждённого журнала | Сохранить копию файла, разбираться с повреждением; не считать его автоматически восстановленным |
| `maintenanceError` при продолжающей работать базе | Проверить причину отдельно; ошибка обслуживания сама по себе не свидетельствует о порче пользовательских данных |

Если `close()` после ошибки тоже выбросил исключение, обработайте его отдельно. Не считайте исход неуспешной записи известным лишь по факту выброшенной ошибки: её подтверждение могло попасть на диск до сбоя следующего шага.
